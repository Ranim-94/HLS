\subsection{Ports on FPGA}

A hardware design exchanges data and control commands with the rest of the system using ports with properly associated interface.

Hardware designs use ports to communicate with other modules on a system.\\ 

Ports have their own hardware structure and can be a simple wire or a complex circuits implementing an interface, realising its sophisticated protocol. Different types of ports are shown  \autoref{fig:input_output:port_example}.

\begin{figure}[h]
\centering
\includegraphics[scale=0.45,frame]{Figures/input_output/port_example}
\caption{Types of Port}
\label{fig:input_output:port_example}
\end{figure}

\begin{itemize}

\item Simple wire

\item 8 bit parallel data bus

\item complex buses such as USB,I2C,$\cdots$


\end{itemize}

For our LED controller project, the \verb|HLS| code is a simple assignment that return a fix value to drive the 8 LEDs.\\

The function argument (that is \verb|*o|) are synthesised into input/output signals in the corresponding hardware design, and we should have some port associated with each of them implmenting some specific interface.\\

In this example, the 8-bit width port implements eight simple wires without any specific protocol (see \autoref{fig:input_output:port_LED_Controller})  

\begin{figure}[h]
\centering
\includegraphics[scale=0.45,frame]{Figures/input_output/port_LED_Controller}
\caption{Port for LED controller}
\label{fig:input_output:port_LED_Controller}
\end{figure}

Now the question is: how can we define this mapping between function arguments and its port interface?

Compiler directive $\leftrightarrow$ \verb|#pragma HLS| will help us in this task.\\

\newpage
Now the compiler directive we use in the LED controller project are used for 2 part:

\begin{figure}[h]
\centering
\includegraphics[scale=0.45,frame]{Figures/input_output/pragma_port_interfaces}
\caption{Compiler directive for port interfaces with function and function arguments}
\label{fig:input_output:pragma_port_interfaces}
\end{figure}

\begin{enumerate}

\item The function argument $\leftrightarrow$ \verb|char *o|

	\begin{itemize}
	\item \verb|#pragma HLS INTERFACE AP_NONE PORT=o| 
	
	\item Since we don’t have any specific interface in this example, the \verb|AP_NONE| is used for this purpose. 
	
	\item In this example, \verb|AP_NONE| interface models a simple wire port in the final hardware design
	\end{itemize}

\item A compiler directive for the \tbi{function itself}

	\begin{itemize}
	\item \verb|#pragma HLS INTERFACE AP_CTRL_NONE PORT=return|
	\end{itemize}

\end{enumerate}

\section{FPGA Structure}

Once the bitstream file is generated, we need to download it to the FPGA baord.

An FPGA is composed form 2 layers: application and configuration layer.\\

An \tbi{application layer}  contains all the \tbi{hardware modules} that can be configured and connected together to implement an \tbi{algorithm or a function}. After configuring this layer, we can apply the input data and get the generated outputs.\\

The \tbi{configuration layer} consists of a set of \tbi{memory cells } used to configure the application layer modules. 
The configuration data saved in this layer is called bitstream and is generated by synthesis tools.

Theoretically, the configuration memories are accessible sequentially, and FPGA bitstream data is written to the FPGA using a streaming scheme.\\

This circuit consists of a simple set of wire connections, which is described using \verb|C| function

\begin{itemize}

\item only circuit functionality or description can be described using a \verb|C| functions 

\item Port and interfaces are designed using \verb|#pragma| directive

\item FPGA pins connections to IO peripheral are desribed in the logic synthesis part, using the constraint file of the associated FPGA board

\end{itemize}

\label{sub:port_interfaces}

Let's see now what is the \verb|C| function used to implement a led controlled by switch. It is shown in \autoref{fig:input_output:C_function_switcheLED}.

The functions states that the input (switche) is directly connected to the LED. The synthesis tool translates this individual assignment into a set of wires that connect the input to the outputs.\\

Now of course what is missing from the \verb|C| function in \autoref{fig:input_output:C_function_switcheLED} is the \verb|pragma| directive so we can add ports and interfaces. Before adding them, we discusse in more details thes concepts: \textit{port and interfaces} .\\

Each hardware module can be described by 1 \verb|C| function, or multiple \verb|C| function calling each other. \tbi{Only one function can be the top function which represents our hardware modukle}, and the other functions need to be called via this top function.\\

\autoref{fig:input_output:function_call_graph} shows a typical call graph, where the \tbi{functions arguments represent the hardware ports}, through which the module communication with the reste of the systme through a spefic protocol (serial communication, synchronise communication,$\cdots$).

\includegraphics[scale=0.45,frame]{Figures/input_output/function_call_graph}
\caption{C function call graph}
\label{fig:input_output:function_call_graph}
\end{figure} 

In order to do this communication, the ports need to be synthesised into digital circuits, and this process is called \tbi{interface synthesis}.\\

\verb|Vitis| IDE performe this systhesis for us, and user should provide \tbi{mode} for this interface. An example of different modes are shown in \autoref{fig:input_output:port_interface_modes_example}.

\item the more the port circuitry is complex, different modes can be used for such a complexity

\end{itemize}

\section{Summary} 

\begin{itemize}

\item HLS general desing points (\ref{sub:hls_desing}):

	\begin{itemize}
	\item \verb|C| function describes the logic circuit
	
	\item Port and interfaces of function argument and fucntion itself using \verb|pragma| diretive
	
	\item FPGA pins connection to IO port using constraint files
	\end{itemize}


\item Function hierachy, Port and Interfaces (\ref{sub:port_interfaces}):

	\begin{itemize}
	\item Only 1 top function can exist representing a hardware module
	
	\item Need port interfaces equal to the number of arguments of the top function
	
	\item And plus one for the function itself, represented by the keyword \verb|return|
	
	\item A top function can't have a pointer as return value because it is not synthesisable
	
	\end{itemize}

\end{itemize}
